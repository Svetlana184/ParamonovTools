## ОТВЕТЫ


1. Что такое паттерн проектирования и какую проблему он решает?
    Паттерн проектирования — это типовое решение часто встречающейся задачи проектирования ПО, шаблон/описание подхода, который можно адаптировать под конкретный язык и контекст.

    Какую проблему решает:
    - позволяет не придумывать каждый раз одни и те же функции

2. Чем порождающие паттерны отличаются от структурных?
    Порождающие работают с моментом и способом создания объектов; структурные — с организацией связей между уже существующими объектами/классами. 

3. В чём разница между Factory Method и Abstract Factory?
    Factory Method — один метод для создания одного продукта. 
    Abstract Factory — интерфейс для создания семейства связанных продуктов (нескольких разных типов, которые должны сочетаться). 

4. Для каких задач лучше использовать Builder?
    Builder уместен, когда:
    - Объект сложный, с множеством параметров, особенно опциональных.
    - Нужно пошаговое конструирование и контроль над процессом.

5. В чём заключается принцип работы Prototype?
    Prototype создаёт новые объекты путём клонирования существующего экземпляра-прототипа, а не через new. Клиент просит прототип «скопировать себя».

6. Почему Singleton может быть нежелателен в крупных проектах?
    Проблемы Singleton:
    Глобальное состояние — скрытые зависимости, непредсказуемость, сложность отладки.
    Скрытые связи — классы неявно зависят от синглтона, что ломает явное внедрение зависимостей.
    Проблемы тестируемости — сложно подменить в тестах (статические/глобальные экземпляры), тесты влияют друг на друга (состояние протекает).
    Нарушение принципа единственной ответственности — класс и создаёт себя, и управляет своим жизненным циклом, и выполняет бизнес-логику.
    Проблемы многопоточности — нужна синхронизация (double-checked locking и т.п.), легко ошибиться.
    Сложность параллельной разработки — единая точка изменения, конфликты в команде.
    Проблемы с масштабированием — в распределённых системах «один на процесс» не означает «один на систему».

7. Чем Adapter отличается от Facade?
    Adapter — «переходник» между несовместимыми интерфейсами. Он оборачивает один объект и приводит его интерфейс к ожидаемому клиентом. 
    Facade — упрощённый единый интерфейс к сложной подсистеме из множества классов. Цель — упрощение и снижение связанности клиента с подсистемой. Facade не меняет интерфейсы отдельных классов — он их объединяет.

8. В чём разница между Bridge и Decorator?
    Bridge — разделяет абстракцию и реализацию на две независимые иерархии, чтобы они могли меняться независимо. 
    Decorator — оборачивает объект, добавляя поведение динамически, не меняя его интерфейс. Декораторы можно нанизывать друг на друга в произвольном порядке, комбинируя функциональность во время выполнения.


9. Как Composite позволяет работать с отдельными объектами и группами одинаковым способом?
    Composite строит древовидную структуру, где и отдельный объект, и «узел» реализуют один и тот же интерфейс (компонент). Клиент вызывает операции единообразно, не проверяя тип.

10. Как Flyweight экономит память?
    Flyweight выносит общее (внутреннее) состояние множества объектов в разделяемые «легковесы», а уникальное (внешнее) состояние хранит снаружи и передаёт при вызове.

    Экономия достигается за счёт:
    - Разделения — один экземпляр используется многими «виртуальными» объектами.
    - Кэширования — фабрика  возвращает уже существующий легковес по ключу, а не создаёт новый.

11. В чём разница между Proxy и Decorator?
    Proxy — «заместитель», контролирующий доступ к объекту. 
    Decorator — «украшение», добавляет обязанности к объекту, обычно нанизываясь цепочкой; реальный объект создаётся извне и передаётся декоратору.


## ПАТТЕРНЫ


1. Создание разных семейств объектов для Windows и Linux
Паттерн: Abstract Factory 
Почему: Требуется создавать семейства взаимосвязанных объектов, которые должны быть согласованы между собой. 

2. Сборка компьютера из комплектующих с необязательными параметрами
Паттерн: Builder 
Почему: Объект сложный, состоит из множества частей, часть параметров опциональна. 

3. Копия сложного игрового персонажа со всеми характеристиками
Паттерн: Prototype 
Почему: Нужно клонировать существующий объект, сохранив всё его состояние (характеристики, инвентарь, навыки), вместо создания «с нуля». 

4. Единственный экземпляр менеджера настроек
Паттерн: Singleton 
Почему: Требуется гарантировать ровно один экземпляр класса с глобальной точкой доступа. 

5. Старая библиотека оплаты несовместима с новым интерфейсом
Паттерн: Adapter 
Почему: Классическая ситуация несовместимости интерфейсов

6. Разные способы отправки уведомлений без изменения клиентского кода
Паттерн: Chain of Responsibility
Почему: если способ отправки выбирается по правилам/условиям

7. Несколько способов отображения одного отчёта: PDF, HTML, текст
Паттерн: Bridge
Почему: Bridge разделяет абстракцию отчёта и реализацию рендеринга, позволяя менять их независимо

8. Файловая система обрабатывает файлы и папки одинаково
Паттерн: Composite 
Почему: Файловая система — это дерево, где «лист» (файл) и «узел» (папка) должны обрабатываться через единый интерфейс, не проверяя тип

9. Добавить объекту дополнительные возможности без изменения класса
Паттерн: Decorator
Почему: Нужно динамически расширять поведение, не трогая исходный класс 

10. Тысячи деревьев с повторяющимися данными в игре
Паттерн: Flyweight
Почему: Тысячи объектов делят общее (внутреннее) состояние. Уникальное (внешнее) состояние хранится отдельно и передаётся при отрисовке

11. Контроль доступа к удалённому объекту через промежуточный объект
Паттерн: Proxy 
Почему: Промежуточный объект представляет другой объект и контролирует доступ к нему

12. Скрыть сложную подсистему отчётов за простым интерфейсом
Паттерн: Facade 
Почему: Есть сложная подсистема из множества классов, и клиенту нужен простой единый вход
